## 普通调用、回调与监听

普通方法调用由调用方明确指定操作，结果沿调用栈返回。例如，客户端调用 process(text) 后取得处理结果，再决定后续操作。调用方可以依赖接口，因此直接调用并不必然造成较强耦合。

回调将后续处理行为作为参数或配置交给另一组件，由该组件在约定时机调用。Java 可用接口对象、匿名类、Lambda 或方法引用表示回调。回调是否异步取决于调用方式，Lambda 本身不会创建线程。

监听机制先将处理器注册到事件源，事件发生后，事件源向监听器传递事件对象并调用处理方法。它适合长期订阅及一对多通知。监听通常通过回调实现，回调最终仍由方法调用完成，三者存在包含关系，并非互斥的底层机制。

## Action 与 ActionListener

题目中的 ActionEvent、ActionListener 和 Swing Action 属于 Java SE 桌面 API。ActionEvent 保存事件来源、动作命令等信息；ActionListener 定义接收方法 actionPerformed(ActionEvent e)。Action 扩展监听接口，将执行行为与名称、图标、提示和启用状态等属性组织在一起，AbstractAction 提供其基础实现。

按钮通过 addActionListener 注册处理器，用户动作发生后调用其 actionPerformed 方法。按钮和菜单还可绑定同一个 Action，共享行为及其支持的属性。例如，action.setEnabled(false) 可以使关联入口同时禁用。动作执行与属性更新是两条通知过程：组件调用动作执行操作，动作的属性变化通知组件更新状态。

Swing 界面事件通常在事件分派线程（EDT）处理。耗时操作应放入后台任务，界面更新返回 EDT。ActionListener 接口本身不保证运行线程，自定义事件源直接调用监听器时，监听器仍在发布线程执行。

## 比较与适用场景

对“校验后保存”等强依赖，应在服务或工作流中明确顺序，不依赖独立监听器的注册次序。页面或任务结束后应注销相应监听器，避免无效通知和对象长期保留。

单线程同步分发中，若有 $k$ 个监听器，第 $i$ 个监听器耗时为 $t_i$，则总耗时近似为

T=T_{\text{事件构造}}+T_{\text{遍历}}+\sum_{i=1}^{k}t_i.

异步分发增加队列和线程协调成本，可减少调用方等待或重叠 I/O，但不保证降低总耗时。

多个异步任务的结果组合可用 CompletableFuture，持续数据流可用支持需求量控制的 Flow，跨进程通知可用发布订阅。非异步的后续处理不保证切换线程，发布订阅也不自动提供可靠送达或恰好一次执行。

## DocAgent 的执行过程

DocAgent 先将文档解析为树形大纲，再由执行智能体按需读取正文、图片和表格并作答；复核智能体补充核查，反思阶段更新阅读指导。大纲提供章节及元素定位，五个工具分别执行关键词搜索、章节读取、图片读取、页图读取和表格图像读取。

作者代码中的 run_experiment.py 顺序调用执行智能体和复核智能体；两者答案字符串不同时调用反思阶段。run_agent 请求模型、读取工具调用、执行工具并回填结果，随后继续请求模型。get_reply_for_tool 按工具名分支调用本地 DocReader 方法。该调用路径使用普通函数调用，未实现 MCP 初始化、工具发现或工具调用协议。

两个智能体通过不同提示和上下文分工，不要求使用不同模型权重。记忆是加入后续提示的字符串，更新记忆不涉及反向传播或模型参数训练。

## ActionListener 的适用范围

ActionListener 可以作为任务启动和完成通知的入口。监听器接到事件后调用调度逻辑，由调度逻辑判断任务依赖、剩余预算和当前状态，再安排后续任务。接口只规定通知方法，不提供这些判断规则。

调度过程可表示为

\delta(s,e)=(s',\mathcal C),

其中 $s$ 为当前状态，$e$ 为到达事件，$s'$ 为更新后的状态，$\mathcal C$ 为待执行命令。监听器传递事件，状态机验证事件是否属于当前运行和调用，再决定状态变化与新命令。

界面可保留 Action，后台宜采用与 Swing 无关的类型化事件，保存运行标识、逻辑调用标识、尝试次数、请求标识和结果。界面禁用状态不能替代服务端权限校验或并发控制。

互不依赖的只读请求可以并发执行；需要初稿的复核应在初稿完成后开始。远程调用放在受控执行器中，不在 EDT 或持有状态锁时等待网络结果。同一运行的状态更新应串行处理，或通过事务版本校验防止重复推进。

## MCP 的调用方式

MCP 由宿主应用、客户端和服务端组成。宿主应用管理模型上下文与权限，客户端维护协议连接，服务端暴露工具等能力。将 DocAgent 接入 MCP 时，可保留角色逻辑，将 DocReader 封装为文档工具服务；此处属于改造方案。协议采用 2025-11-25 版本。

基本流程为：客户端发送 initialize 协商版本和能力，接收响应后发送 notifications/initialized；随后用 tools/list 取得工具名称及参数结构，用 tools/call 调用工具，按请求标识匹配结果。工具列表分页时需继续获取后续页。

## 失败处理与安全限制

协议错误与工具业务失败应分别处理：畸形请求等使用 JSON-RPC 错误，工具执行失败可返回 isError=true。收到 result 不一定意味着业务成功。

调用超时只说明本地停止等待，不证明远端停止执行。普通请求通过取消通知申请停止，长任务使用 tasks/cancel；取消与完成可能竞争，迟到结果不能重新激活终态任务。

暂时性故障可有限重试，参数错误应先修正参数。每次尝试使用独立请求标识，逻辑调用标识保持不变。写入工具还需业务幂等键，新的请求标识不能阻止重复副作用。文档读取固定版本，避免重试时混入不同版本的内容。

宿主应用和服务端分别校验工具、参数及文档权限。文档与工具输出中的指令作为不可信内容处理，不能改变系统权限；敏感操作保留用户确认。远程连接按授权要求部署，本地 HTTP 服务校验请求来源并限制绑定地址。

## 局限与实现问题

多轮读取和复核增加延迟，较短的单次上下文也不等于较低的累计请求成本。原文讨论了通用模型领域知识不足和仅在英语数据上评估的限制，并考察了结构扰动与任务顺序；中文技术文档、跨版本资料及恶意内容仍需补充验证。

复核可能修正初稿，也可能将正确答案改错。设初稿正确率为 $p$，错误初稿被修正的条件概率为 $r$，正确初稿被改错的条件概率为 $f$，则

p'=p(1-f)+(1-p)r,\qquad p'-p=(1-p)r-pf.

复核有收益的条件是 $(1-p)r>pf$。两个角色给出一致答案不能证明正确，其证据也可能同源。
